# RULES

Этот файл задает рабочие правила для людей и ИИ-агентов в мобильном приложении.
Его цель: уменьшить лишние поиски по проекту, ускорить внесение изменений и сохранить единый стиль кода.

## О приложении

`language-dictionary` — мобильное приложение для изучения иностранных слов через карточки.
Его базовая механика похожа на физические карточки или листочки: с одной стороны слово, фраза или предложение, с другой — перевод.

Основная сущность приложения — карточка.
Карточка может содержать:

- одно или несколько слов
- фразы или предложения
- выбранный язык карточки
- перевод

Главная пользовательская цель — быстро создавать карточки, удобно возвращаться к ним в практике и отслеживать свой прогресс в изучении языка.

Ключевые экраны и сценарии:

- Главный экран: минималистичный список карточек с поиском, фильтрацией, сортировкой и добавлением новых карточек.
- Практика: просмотр карточек в удобном формате с анимацией и возможностью задавать карточке нужный статус в процессе обучения.
- Профиль: статистика, достижения, редактирование профиля, выход из аккаунта и удаление аккаунта.
- Итоги года: экран с годовой сводкой пользователя; формат может меняться, но смысл экрана всегда в показе итогов года.
- Настройки: настройка отображения карточек в списке, описание приложения, язык приложения, связь с разработчиком и информация о версии приложения.

При любых изменениях важно помнить:

- это не абстрактный "словарь", а продукт про личное изучение слов через карточки
- ключевой UX строится вокруг простоты но красоты, анимации для удержания пользователя, скорости и удобства регулярной практики
- список карточек, создание карточек и практика — центральные сценарии приложения

## 1. Главный принцип

Не изобретай новое, если в проекте уже есть похожее решение.

Перед добавлением нового кода сначала проверь:

- `src/shared/UI` для базовых UI-компонентов
- `src/shared/hooks` для повторно используемой логики
- `src/shared/store` для состояния
- `src/shared/styles/unistyles.ts` для цветов, размеров и дизайн-токенов
- соседние `*.styles.ts` и похожие экраны/модалки для визуальных паттернов

Если рядом уже есть рабочий паттерн, расширяй его, а не создавай альтернативу.

## 2. Приоритет решений

При конфликте ориентируйся в таком порядке:

1. Существующий код и паттерны рядом с изменяемой фичей.
2. Переиспользуемые общие слои: `shared`, `entities`, `widgets`.
3. Правила из этого файла.
4. Новые абстракции только если без них решение действительно начинает дублироваться.

Цель: минимальный, предсказуемый и локальный diff.

## 3. Как работать по проекту

Перед реализацией:

1. Найди ближайший похожий экран, виджет, модалку или хук.
2. Проверь, нет ли уже готового UI-компонента, иконки, цвета или helper-функции.
3. Вноси изменения в текущую структуру проекта, не ломая ее под новую задачу.

Во время реализации:

1. Держи логику рядом с зоной ответственности компонента.
2. Не раздувай родительские компоненты лишними пропсами и обработчиками.
3. Если часть кода стала самостоятельной по смыслу, выноси ее в отдельный файл.

После реализации:

1. Проверь, что новый код визуально и архитектурно совпадает с соседним.
2. По возможности запускай `yarn lint` и релевантные проверки.

## 4. Архитектурные ориентиры

Проект построен как React Native + TypeScript приложение со слоистой структурой:

- `app` — инициализация приложения и навигация
- `pages` — экраны
- `widgets` — крупные блоки интерфейса
- `features` — пользовательские сценарии и модалки
- `entities` — доменные сущности
- `shared` — UI, hooks, store, helpers, constants

Новые изменения должны укладываться в эту модель. Не смешивай экранную, доменную и общую логику без причины.

## 5. Обязательные правила

### TypeScript

- `let` запрещён полностью, это ошибка линтера (`no-restricted-syntax` на `VariableDeclaration[kind="let"]` в `.eslintrc.js`), а не просто рекомендация. Используй `const`: для значений, которые раньше пересчитывались через `let` в цикле, применяй `reduce`, рекурсию или пересобирай значение через тернарник/раннюю функцию вместо переприсваивания. Если нужен мутируемый счётчик или ссылка на модульном уровне (например, id-генератор, реестр колбэка), заверни его в `const`-объект вида `{ current: ... }` и мутируй поле, а не саму переменную.
- Не использовать `any`.
- Если тип неочевиден, опиши его явно или переиспользуй существующий.

### React и компоненты

- Используй существующие компоненты, если они уже решают похожую задачу.
- Большие компоненты разбивай на части, чтобы файл не становился перегруженным.
- Не объявляй функции прямо в JSX. Выноси их в тело компонента.
- Разрешено использовать `map` прямо в JSX для рендера списков, если там нет новой бизнес-логики.
- JSX не хранить в переменных без явной необходимости.

### Memoization policy

- Все значения и функции, зависящие от состояния или пропсов, стабилизируй через `useMemo` или `useCallback`, если это соответствует текущему стилю проекта.
- Сам JSX, JSX-узлы и простые элементы списка дополнительно мемоизировать не нужно.
- Динамические стили не писать inline-объектами в JSX. Выноси их в `useMemo` или в `*.styles.ts`, если стиль статический.

### Стили и UI

- Соблюдай существующий дизайн, визуальный ритм и стиль проекта.
- Используй существующую палитру и размеры из `src/shared/styles/unistyles.ts`.
- Если нужного цвета нет, сначала проверь, нельзя ли переиспользовать текущий; новый цвет добавляй централизованно.
- Стили компонентов по умолчанию держать в соседнем `*.styles.ts`.
- Соблюдай семантику верстки и аккуратную структуру JSX.

### Изображения

- Для отображения изображений использовать **только** `react-native-fast-image`. Никогда не использовать `Image` из `react-native`.
- `resizeMode` передавать через проп компонента (`resizeMode={FastImage.resizeMode.cover}`), а не через стиль.

### Локализация и текст

- UI-текст должен оставаться на русском, если задача не требует другого.
- При изменении файлов с русским UI-текстом сохраняй совместимость с текущей кодировкой проекта. Если файл уже ожидается в `UTF-8 with BOM`, не меняй это поведение.

## 6. Порядок хуков в компоненте

Соблюдай текущий локальный порядок, если компонент использует эти хуки:

1. `useNavigation`
2. `useRoutes`
3. `useActions`
4. `useAppDispatch`
5. `useAppSelector`
6. `useState`
7. `useAnyQueryApi`
8. `useCustomHooks`
9. `useMemo`
10. `useCallback`
11. `useEffect`

Если часть списка в компоненте не используется, просто пропускай ее.

## 7. Правило ответственности компонента

Компонент должен содержать свою собственную прикладную логику, если она относится именно к нему.

Пример:

- если модалка удаляет сущность, логика удаления должна жить в модалке
- не выноси такую логику в родителя без необходимости
- не раздувай интерфейс компонента множеством технических пропсов

Исключение: если логика реально общая и уже переиспользуется в нескольких местах, ее можно вынести в `hook`, `helper` или `shared`-слой.

## 8. Что особенно ценит ИИ-агент в этом проекте

- Сначала искать существующий паттерн, потом писать код.
- Делать локальные изменения вместо широких рефакторингов.
- Не плодить новые сущности, файлы и абстракции без явной пользы.
- Поддерживать читаемость для человека: короткие компоненты, понятные имена, предсказуемая структура.

## 9. Антипаттерны

Не делай без необходимости:

- новый UI-компонент, если уже есть похожий в `shared/UI`
- новый цвет, если уже есть близкий в палитре
- inline-функции в JSX
- inline-стили-объекты в JSX
- `any`
- большой монолитный компонент
- перенос логики компонента в родителя только ради "контроля сверху"

## 10. Критерий хорошего изменения

Хорошее изменение в этом проекте:

- похоже на уже существующий код
- не ломает структуру слоев
- минимально по объему
- читается человеком без дополнительных объяснений
- не заставляет следующего агента заново разбираться, "как тут принято"
